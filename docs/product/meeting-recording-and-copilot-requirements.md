# 会议记录与会议 Copilot 需求基线

状态：已确认需求基线

日期：2026-08-25

适用产品：Muse Desktop，后续可扩展到 Web 与移动端配套入口

## 1. 文档目的

本文从第一性原则定义 Muse 的两项会议能力，并固定二者的独立边界与依赖关系：

1. **完整会议记录**：独立完成会议采集、转写、归档与会后分析。
2. **会议 Copilot**：在完整会议记录提供的实时会话事实之上，结合会议前文与用户选择的 Muse 资料，向用户提供实时回答辅助。

本文是需求与验收边界，不是技术实现方案、排期或发布承诺。未在“已确认决策”中列出的内容，不应被当作已经确定的产品结论。

## 2. 第一性原则

### 2.1 会议事实先于 AI 推断

会议中真实发生的声音、说话人、时间和原始内容，是后续转写、总结和回答辅助的事实来源。AI 产生的摘要、行动项和回答建议都是派生结果，不能覆盖、篡改或替代原始记录。

### 2.2 会议记录具有独立价值

用户即使不开启 Copilot，也需要可靠地记录、回看、搜索和复盘会议。因此“完整会议记录”必须能够独立启用、独立运行、独立验收，不得依赖回答模型、Agent、Skill、MCP 或外部知识检索。

### 2.3 Copilot 是可选辅助，不是会议记录的前提

会议 Copilot 消费会议记录产生的实时转写和上下文，但 Copilot 的关闭、失败、超时、限流或资料不足，不得中断录音、破坏转写或造成会议档案缺失。

### 2.4 有依据的回答优先于看似完整的回答

Copilot 的目标不是在所有问题上都给出肯定答案，而是在可用时间内给出尽可能正确、可说出口、可追溯的辅助。资料不足或存在冲突时，应明确表示不确定，并提供安全的回答边界，禁止编造数字、事实或承诺。

### 2.5 人承担最终判断和表达责任

Copilot 只向使用者提供建议，不代表用户自动发言，不替用户向会议发送文本或语音，也不自动作出承诺。用户决定是否采用、如何修改和如何表达建议。

### 2.6 权限和知情同意是功能边界

系统权限只说明设备所有者允许 Muse 采集音频，不代表其他参会者已经同意被录音。产品必须持续显示明确的录音状态，并要求用户遵守适用法律、组织制度和会议约定。

## 3. 两项需求的关系

```text
完整会议记录（需求一）
├── 会话生命周期
├── 麦克风与系统音频采集
├── 实时转写
├── 录音与逐字稿归档
├── 会后校正与分析
└── 搜索、导出、关联与共享
             │
             │ 提供实时会话事实和已授权资料
             ▼
会议 Copilot（需求二）
├── 当前问题识别
├── 会议前文组装
├── Muse 文档与 Project 资料检索
├── Agent 与 Skill 约束
├── 快速回答提示
├── 深度检索与扩展回答
└── 引用、可靠性和风险提示
```

依赖规则：

- 需求一不依赖需求二。
- 需求二依赖需求一提供的实时转写、说话人和时间线，但不能反向控制需求一的录音生命周期。
- 两项需求可以共享音频、转写、文档引用和组织权限等基础能力，但业务状态、错误状态和验收结论必须分离。

## 4. 需求一：完整会议记录

### 4.1 用户问题

用户在视频会议、语音通话、线上答辩、访谈、评审或其他会话中，需要完整保存自己与对方的交流内容，并在会后获得可回看、可检索、可复盘、可继续处理的会议档案。

用户当前面对的主要问题是：

- 仅依赖记忆或手工笔记会遗漏信息；
- 单独录麦克风会丢失远端参会者声音；
- 只有音频难以快速定位和复盘；
- 自动转写可能存在说话人、时间和文本错误；
- 总结与行动项如果没有原始证据，难以核对；
- 会议结果与 Muse 的 Project、文档和任务脱节，后续仍需人工搬运。

### 4.2 用户结果

一次会议结束后，用户应获得一份完整、可恢复、可核对的会议档案，包括：

- 原始会议音频；
- 自己与对方可区分的音频来源；
- 带时间戳和说话人信息的逐字稿；
- 可回放并跳转到对应文本的时间线；
- 会后校正后的最终转写；
- 会议摘要、主题、决策、行动项和未解决问题；
- 与 Project、文档、任务和参与者的关联；
- 可搜索、可导出、可按权限共享的归档记录。

### 4.3 核心功能要求

#### 4.3.1 会话生命周期

系统应支持：

- 创建会议；
- 手动开始录音；
- 正常停止；
- 取消尚未形成有效内容的会话；
- 展示录音时长和当前状态；
- 在用户切换 Muse 页面时继续录音；
- 对异常退出、页面刷新、进程崩溃、设备变化和网络中断提供可见的恢复或失败结果。

录音必须由用户明确发起。检测到会议软件、摄像头或麦克风正在使用时，系统可以提示用户开始记录，但不得静默自动录音。

正常会话不提供暂停或跨天继续功能。用户切换到 Muse 的其他页面、窗口暂时失去焦点或会议中出现长时间静音时，录音仍由后台持续运行；只有用户明确点击“结束记录”才进入停止与封存流程。“记录进行中”入口仅在当前确有活动记录时显示，封存完成后立即消失。应用崩溃、系统休眠等导致采集无法继续时，本次记录标记为已中断并保留已写入内容，不重新进入活动记录。

实时转写的 `record timeout`、网关断线或短暂请求超时只触发转写流自动重连，不改变录音生命周期；重连期间原始音频必须继续独立写入。

#### 4.3.2 音频采集

系统应把音频至少区分为两类来源：

- `local`：用户自己的麦克风；
- `remote`：会议软件或系统播放的对方声音。

两类来源应尽可能独立采集、独立监控和独立持久化。任何一路失效时，系统必须明确提示，不能在只有单路音频的情况下继续显示“录音正常”。

系统应处理或明确报告以下情况：

- 用户可以在开始记录前枚举并选择当前可用的麦克风输入设备，而不是只能使用系统默认设备；
- 进入记录准备页和切换麦克风设备只做设备枚举，不得自动打开麦克风或系统音频；音频探测、人声测试和正式记录都必须由用户明确触发；
- 选择麦克风后，用户可以执行一次明确的人声测试；测试过程中必须实时展示连续输入电平和“正在说话”状态，结束后再给出结果，不能只在最后返回一个 RMS 数值；
- 麦克风已被会议软件使用；
- 会议软件选择了非系统默认麦克风；
- 使用内置扬声器导致远端声音泄漏进麦克风；
- 使用 AirPods、蓝牙耳机或外置声卡；
- 录音中切换输入或输出设备；
- 所选麦克风失效或被拔出时必须单独告警，不得静默回落到其他输入设备；
- 音频 API 返回成功但持续没有有效样本；
- 系统休眠、锁屏或唤醒；
- 存储空间不足或写盘失败。

#### 4.3.3 实时转写

系统应在会议进行中持续生成可见的转写，并至少保存：

- 文本；
- 来源或说话人；
- 开始时间；
- 结束时间；
- 是否为临时结果或最终结果；
- 可用时的置信度。

临时结果可以更新，但已经确认的最终结果不得被无依据地覆盖。转写失败不得影响原始录音继续写入。

#### 4.3.4 归档与恢复

会议档案应保存独立的处理状态，包括但不限于：

- 录音中；
- 已停止；
- 待转写；
- 转写中；
- 待分析；
- 分析中；
- 已完成；
- 部分完成；
- 失败。

“部分完成”必须能表达实际边界，例如：麦克风轨完整、系统轨缺失；原始录音完整、会后分析失败。不得用一个笼统成功状态掩盖材料缺失。

系统应持续写入足以恢复的录音片段或检查点，避免长时间录音只在停止时一次性落盘。

#### 4.3.5 会后处理

会议停止后，系统应允许：

- 使用完整音频重新生成更高质量转写；
- 校正说话人和段落；
- 用户编辑逐字稿且保留原始转写来源；
- 生成摘要；
- 提取决策；
- 提取行动项、负责人和截止时间；
- 提取未解决问题和风险；
- 从行动项创建 Muse 任务；
- 重新运行失败的转写或分析，而不重复录音。

#### 4.3.6 检索、导出和关联

用户应能够：

- 按标题、时间、Project、参与者、标签和正文搜索会议；
- 从逐字稿跳转到对应音频位置；
- 把会议关联到 Muse Project、文档和任务；
- 导出至少一种人类可读格式和一种结构化格式；
- 根据权限把会议档案分享给组织成员；
- 删除原始音频但保留文字材料，或删除整场会议。

会议档案默认永久保存。删除原始音频时，逐字稿、会后分析和 Copilot 历史继续保留；删除整场会议时，会议记录、转写、分析、Copilot 历史、权限与文件引用一并失效。只有不再被其他业务对象引用的服务端音频对象才进入物理清理。

具体导出格式、共享粒度和组织级保留管理属于后续产品设计，不在本文锁定。

### 4.4 独立性要求

在以下条件下，完整会议记录仍必须可用：

- Copilot 未启用；
- 没有选择 Agent 或 Skill；
- 没有添加任何文档；
- 回答模型不可用；
- MCP 不可用；
- 外部网络不可用但本地采集能力正常；
- 会后分析暂时失败。

### 4.5 需求一验收标准

需求一只有在以下事实同时成立时才能判定完成：

1. 用户能够明确开始和停止一次会议记录。
2. 在支持的系统和设备组合中，本地麦克风与远端系统音频都产生持续有效的音频数据。
3. 界面分别显示两路音频健康状态；任一路中断会得到明确告警。
4. 用户切换 Muse 页面后录音继续，不依赖当前会议页面保持前台。
5. 会议中可以看到带来源和时间的实时转写。
6. 停止后可以重新打开会议档案并播放录音、查看逐字稿。
7. 原始录音仍在时，转写或分析失败可以单独重试。
8. 长时间录音不会因 Renderer 刷新或单个 AI 请求失败而整体丢失。
9. 用户可以获得可核对的摘要、决策、行动项和未解决问题。
10. 用户可以搜索和导出会议，并按权限关联或共享到 Muse 业务对象。
11. 不启用 Copilot 时，上述能力仍完整成立。

具体支持的最长录音时长、性能预算、转写延迟和准确率阈值，需要在技术 Spike 与真实会议基线测试后确定，不能在没有测量的情况下虚构。

## 5. 需求二：会议 Copilot

### 5.1 用户问题

用户在项目答辩、技术评审、销售沟通或其他线上会议中，可能无法及时回忆项目事实、精确数字、历史讨论或资料中的依据。用户需要 AI 在不替代本人表达和判断的前提下，理解对方当前问题，并基于会议前文与用户授权的资料，快速给出可说出口的回答提示。

### 5.2 依赖条件

Copilot 依赖需求一至少提供：

- 正在进行的会议会话；
- 可区分本地与远端的实时转写；
- 稳定的时间线；
- 最近对话；
- 用户已授权的会议资料。

Copilot 不得直接操作录音文件或决定录音何时停止。它只消费经过会议记录层发布的事件与只读上下文。

### 5.3 用户结果

当对方提出问题时，用户应能在问题仍具有时效性的窗口内看到：

- 系统识别出的当前问题；
- 简短、可说出口的建议回答；
- 2–4 个关键回答点；
- 回答所依据的会议前文或 Muse 资料；
- 资料不足、冲突或不确定时的风险提示；
- 可选的深入回答、可能追问或进一步检索。

Copilot 的输出是建议，不自动发送给会议软件，不自动朗读，也不替用户作出承诺。

### 5.4 会前配置

用户应能够在会议前选择或准备：

- 关联的 Project；
- 参与会议的 Agent；
- Agent 携带的 Skill；
- Muse 文档、表格、PDF、本地文件或其他有权访问的资料；
- 会前说明或 Brief；
- 回答风格；
- 是否允许使用模型一般知识；
- 是否允许调用 MCP、Web 或其他外部工具；
- 是否开启 Copilot。

Copilot 默认关闭。会前开关只决定会议开始时的初始状态，不是整场会议不可更改的配置。用户可以在 Copilot 关闭的状态下开始记录，并在记录进行中随时开启或再次关闭；这些操作不得暂停、重启或改变录音与实时转写状态。

资料应尽量在会议开始前完成解析和索引。系统不得把“用户已经选择资料”等同于“资料已经可用于检索”；需要分别展示准备中、可用和失败状态。

### 5.5 会中触发方式

Copilot 至少应支持手动触发：用户通过快捷键或按钮要求判断并处理当前最新的完整发言。

自动识别问题是可选增强。开启后，每个新的完整发言都应连同采集通道、最近上下文、静默边界和冷却状态交给回答模型，由模型判断是否需要回应；`local`/`remote` 只表示本地麦克风或系统音频采集通道，不得被硬编码为“用户本人”或“对方”。系统仍需通过 final 边界、重复检测和冷却时间避免对同一发言重复请求，普通陈述、寒暄或不需要回应的内容由模型返回 `no_action`。

自动触发失败或误判时，不影响手动触发。

记录进行中开启 Copilot 时，Copilot 可以只读使用本场会议已经形成的逐字稿和已准备资料组装上下文，不要求重新开始录音。关闭 Copilot 后，系统应停止自动问题识别和新的回答生成；已经产生的建议与来源记录仍保留，录音、实时转写和会后处理继续运行。

### 5.6 上下文组装

Copilot 不应在每次回答时无差别发送完整会议全文。每次回答至少应从下列层次按需组装上下文：

1. 当前问题；
2. 最近若干轮对话；
3. 本场会议的滚动事实摘要；
4. 用户会前 Brief；
5. 从已授权 Muse 资料中检索到的相关片段；
6. Agent 身份、Skill 和回答政策；
7. 用户明确允许时的模型一般知识或外部工具结果。

完整逐字稿继续由需求一保存，供回溯和会后处理使用。

### 5.7 动态添加资料

会议中应允许用户添加 Muse 文档或其他资料。系统必须展示资料状态：

- 准备中；
- 可用于回答；
- 处理失败；
- 权限不足；
- 已移除。

资料未准备完成前，不得在回答中把它描述成已检索依据。引用应能够定位到具体资源及其版本或快照，避免文档后续修改导致历史建议无法核对。

### 5.8 回答策略

Copilot 应支持至少以下策略边界：

- **严格依据**：只使用会议前文和已授权资料；资料不足时明确回答边界。
- **辅助知识**：优先使用已授权资料，模型一般知识必须显式标记。
- **深度检索**：用户明确触发后，允许调用已授权 MCP、Web 或其他工具，并接受更高延迟。

回答中涉及数字、日期、承诺、状态和范围时，应优先给出引用；来源冲突时应展示冲突，不能静默选择一个看似合理的值。

### 5.9 快速与深度通道

为同时满足时效性与正确性，Copilot 应把能力拆为：

- **快速通道**：使用已经准备好的会议前文和资料，流式返回简短要点，不运行开放式长工具链。
- **深度通道**：用户明确触发后，允许完整 Agent、MCP 和外部检索，返回更严谨的扩展回答。

快速通道失败不应自动升级为高成本或高权限深度通道；是否深入由用户控制。

### 5.10 输出要求

默认建议卡应优先显示：

- 一句话结论；
- 2–4 个可说出口的要点；
- 关键数字或事实；
- 来源；
- 可靠性或资料不足提示。

长篇回答、引用原文、可能追问和深入分析作为展开内容，避免用户在会议中阅读大段文字。

### 5.11 故障与降级

发生以下情况时，Copilot 应独立降级并明确显示原因：

- 没有识别出完整问题；
- 实时转写延迟或缺失；
- 文档尚未索引；
- 文档权限被撤销；
- RAG 未找到足够证据；
- 模型超时、限流或不可用；
- MCP 或 Web 查询失败；
- 回答来源冲突；
- 用户关闭 Copilot。

任何 Copilot 故障都不得停止、暂停或污染需求一的录音、逐字稿和会议档案。

### 5.12 需求二验收标准

需求二只有在以下事实同时成立时才能判定完成：

1. 用户能够在一场正常记录的会议中单独开启或关闭 Copilot。
2. 用户可以在会前选择 Agent、Skill 和有权访问的 Muse 资料。
3. 用户能够通过明确操作请求判断并处理当前最新的完整发言，无论该发言来自本地麦克风还是系统音频。
4. 建议回答使用当前问题、最近对话和已准备资料，而不是只依据孤立的最后一句话。
5. 默认输出是简短、可说出口的要点，并在生成过程中流式呈现。
6. 使用资料事实时显示可核对的来源；资料不足时不编造答案。
7. 会议中新增资料时，只有准备完成后才进入回答上下文。
8. 用户可以请求深入回答，但深度工具链不会阻塞录音和实时转写。
9. 用户关闭 Copilot 或模型请求失败后，需求一继续正常运行。
10. Copilot 不会自动向会议发送文本、语音或控制会议软件。

实时回答的目标延迟、首个提示时间、检索质量和建议采用率，需要通过真实答辩与会议样本建立测量基线后再确定。

## 6. 共享约束

### 6.1 数据与权限

- 音频、逐字稿、会议分析和 Copilot 建议是不同数据类型，应支持不同的存储、同步、共享和删除策略。
- 有效会议的原始音频默认同步到 Muse 服务端对象存储。对象存储 provider 可以是 VPS 持久卷上的 `local`，也可以是阿里云 `aliyun`；二者使用同一文件 API 和权限语义。`local` 表示服务端存储，不表示录音只留在发起会议的客户端，因此同样支持跨设备读回。
- Electron `userData/meeting-recordings` 中的录音是采集、断线和崩溃恢复所需的本机缓存；服务端对象文件是跨设备会议档案。服务端同步失败不得删除本机可恢复副本，文字同步失败也不得阻塞音频归档，二者分别显示状态并可独立重试。
- 用户选择文档不代表 Copilot可以绕过资源权限；权限变化后必须停止继续使用无权访问的资料。
- 发送给 ASR、LLM、Embedding、MCP 或 Web 服务的数据范围必须可解释，并受用户和组织策略约束。
- 删除会议时，应明确哪些原始数据、派生结果、引用关系和审计记录会被删除或保留。

### 6.2 可见状态

录音、系统音频、麦克风、实时转写、会后分析和 Copilot 应分别显示状态。一个绿色总状态不能掩盖其中某一路失效。

### 6.3 证据与可追溯性

- 原始会议事实与 AI 派生内容必须可区分。
- 会后分析应能回到对应逐字稿或音频时间点。
- Copilot 建议应记录触发问题、所用资料、模型、时间和来源。
- 用户编辑后的逐字稿或总结应与机器原始结果保持可区分关系。

### 6.4 屏幕共享

会议提示窗口可能在用户共享整个屏幕时被对方看到。隐藏或内容保护只能作为尽力而为的能力，不能承诺所有会议软件和 macOS 版本都能排除提示窗口。产品应优先引导用户分享单个应用窗口、使用第二显示器或使用配套移动端查看提示。

## 7. 明确非目标

当前两项需求不包含：

- 静默、隐蔽或未经用户发起的自动录音；
- 自动替用户在会议中发言；
- 自动把建议发送到聊天框或会议软件；
- 保证 AI 回答绝对正确；
- 保证提示窗口对所有屏幕共享方式不可见；
- 默认授予 Copilot 全部 Muse 文档、MCP 或设备权限；
- 因 Copilot 失败而丢弃或停止会议记录；
- 在没有实测依据时承诺具体平台、设备、录音时长、延迟或准确率。

## 8. 已确认决策

以下内容已经明确，后续实现不得再次混淆：

1. 当前有且只有两项已确认需求：完整会议记录、会议 Copilot。
2. 完整会议记录是独立功能，不是 Copilot 的附属功能。
3. 会议 Copilot 建立在完整会议记录的实时上下文之上。
4. Copilot 可以结合会议前文和用户选择的 Muse 文档资料提供回答辅助。
5. 用户后续可以在会议中继续添加 Muse 资料，但资料就绪状态必须可见。
6. Copilot 只提供提示，用户承担最终回答与判断责任。
7. Copilot 的任何失败都不能影响会议记录的完整性。
8. Copilot 默认关闭；会前开关只决定 Copilot 的初始状态，用户可以关闭 Copilot 开始记录，并在记录进行中随时开启或再次关闭。
9. 记录准备必须允许用户选择麦克风设备并主动进行人声测试；测试弹窗需在说话过程中实时显示输入波动和“正在说话”状态，正式录音使用所选设备，失效时明确告警而不是静默回落。
10. 打开准备页和切换设备不得自动打开任何音频输入；用户明确触发重新检查、人声测试或开始记录后才允许申请音频。
11. 有效会议的原始音频默认同步到服务端对象存储，并通过统一 API 支持跨设备读回和流式回放；`local` 与 `aliyun` 只是服务端存储 provider 的不同实现，不改变产品语义。
12. 会议档案默认永久保存，同时保留“删除原始音频但保留文字材料”和“删除整场会议”两种删除操作。
13. 实时转写只使用云端 ASR，不建设本地 ASR 兜底；云端 ASR 不可用时录音仍继续，实时转写单独显示失败或恢复状态。
14. Copilot 问答历史随会议档案持久化到服务器，供跨设备查看、权限共享和任务交接；删除整场会议时一并删除。
15. 组织内 viewer 可以创建自己的会议并上传该会议的音轨；该能力只授权本人会议的创建与设备写入，不授予其修改其他成员会议的权限。

## 9. 尚未确认的产品决策

以下内容需要后续单独决策，不在本文代替用户拍板：

- 一级入口最终命名与信息架构；
- 首发支持的 macOS 最低版本和会议软件范围；
- 是否以及何时支持 Windows、Linux、Web 和移动端独立采集；

- 自动问题识别是否进入首版；
- 悬浮窗、第二显示器和移动端提示的优先级；
- 具体导出格式；
- 计费、配额和套餐边界；
- 具体性能、延迟和准确率 SLO。

## 10. 交付门槛

需求一应先形成独立可验收的最小完整闭环。需求二可以复用并提前验证需求一发布的实时事件，但不能在需求一尚未证明录音、转写和归档完整时，把 Copilot 演示当作会议能力已经完成。

最终验收应分别报告：

```text
完整会议记录：通过 / 部分通过 / 未通过
会议 Copilot：通过 / 部分通过 / 未通过
```

不得用“Copilot 能生成回答”替代对录音完整性的验收，也不得用“录音文件存在”替代对 Copilot 依据、延迟和降级行为的验收。
